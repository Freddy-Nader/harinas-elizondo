## How to execute the open plans

This is the method that ran plans 001 to 008. Follow it again with `/improve execute plans/README.md`.

1. **One worktree per plan.** The Agent tool's worktree isolation fails in this repo because `.claude` is a symlink. Create each worktree by hand from the tip of the PR branch, for example `git worktree add ../dsw-worktrees/plan-009 -b test/component-reportes-bitacora --no-track chore/improve-plans`, then start the executor without isolation and tell it to work only in that folder.
2. **Executor model.** Sonnet for 009, 010 and 011. Opus for 012.
3. **Parallel work.** 009, 010 and 011 touch different files and can run at the same time. Start 012 after they are approved and on the PR branch, so the report describes the final state.
4. **Databases.** Docker is not running on the operator machine. A Homebrew Postgres runs at localhost:5432. Each executor creates its own throwaway database (`createdb harinas_plan0NN_test`), uses `TEST_DATABASE_URL=postgresql://localhost:5432/harinas_plan0NN_test`, and drops it at the end. Nobody uses the real `DATABASE_URL` for a test.
5. **Ports.** Never 3000. Give each executor its own port (`E2E_PORT=31NN`).
6. **Environment.** When a build needs variables, load `/Users/freddy/Developer/dsw/.env.local` inside the same shell command and never print it.
7. **Review.** The advisor re-runs the done criteria in the worktree, reads the whole diff, and sends the executor back at most twice. Reports from executors are not proof.
8. **One PR.** Approved commits are cherry-picked onto `chore/improve-plans` in the main checkout, the four checks run on the combination, and the branch is pushed to `origin` (the fork). It feeds the draft PR https://github.com/ValleryR/harinas-elizondo/pull/47. Update the PR description after each plan. Commits carry no AI attribution.
9. **Index.** The advisor updates the status row here in the same push.
